Frank Grimes

Disciplined Falsification Review. A pessimistic iteration loop for systematically destroying, rebuilding, and hardening ideas. Assumes everything is broken until proven otherwise.

Philosophy Everything is crap until proven otherwise.

Start here

Frank Grimes is a structured critique process. Load the skill, point it at something, and watch it try to prove the thing wrong. When it can't find meaningful flaws anymore, you have earned confidence, not through hope but through survival.

  1. 1

    Load the skill

    The portable skill lives in skill/SKILL.md. Load it into your agent's skill system. See Providers for provider-specific setup.

  2. 2

    Install jq

    Required for the auto-loop stop hook. brew install jq on macOS, apt-get install jq on Linux.

  3. 3

    Run a grind

    Invoke the skill on your target, a file, a directory, recent changes, or a description. The skill guides you through scope, categories, and mode.

  4. 4

    Read the report

    Every grind produces a structured Grimes Report with a verdict (GREEN/YELLOW/RED), risk register, and Grimey's final word.

Providers

Frank Grimes is provider-neutral. The core skill and stop hook work with any agent that can load markdown skills and execute bash scripts. Adapters make integration trivial.

Claude Code

.claude/skills/

Copy the adapter files into your project's .claude/ directory, or symlink the skill.

mkdir -p .claude/skills
ln -s ../../skill .claude/skills/frank-grimes

Invoke with /frank-grimes:grind <target>.

The Grimes Grind

Six phases. Evidence-first throughout. The objective is not to prove the idea right; it's to prove the default assumptions wrong.

01

The Grimey Read

Absorb the target without trusting it. Look for what is being hidden, glossed over, or assumed. Ask at most 3 clarifying questions, then proceed with labeled assumptions.

02

Default Assumptions

Assume the subject is broken in every way: LLM slop, unreliable, insecure, poorly planned, non-production-ready, unmaintainable, fragile, edge-case blind, compliance-violating, dependency-ridden.

Your objective is to prove these assumptions WRONG.

03

The Grind

Systematically attack across 23 critique categories. Evidence-first: show the specific code path BEFORE describing the risk. Prioritize by Severity × Likelihood × Blast Radius.

04

The Rebuild

For each issue, propose a fix. In fix mode, apply the fixes. In report mode, document only. If a fix is impossible, document the accepted risk.

05

Scoped Re-Grind

Take the updated version and grind again, focusing on the regression scope of the fixes. Note any new risks introduced by the fixes.

06

Stop Conditions & Verdict

Determine the verdict based on P0/P1 mitigation status, verification existence, and observability.

VerdictMeaning
GREEN All P0 mitigated or accepted with timeline. All P1 have mitigations or plan. Verification exists. Observability sufficient.
YELLOW P0 mitigated but P1 evidence weak. Verification path non-comprehensive.
RED Any P0 lacks mitigation. No verification path. Observability insufficient.

Benchmark

The benchmark/ directory contains a framework for validating grind quality across different target types. Designed for A/B testing: swap the skill, run the benchmark, compare scores.

What it measures

  • Evidence Quality: Specific, verifiable evidence for each issue
  • Category Coverage: Attack across multiple categories
  • Severity Assessment: Correct P0/P1/P2/P3 classification
  • Verdict Accuracy: Verdict justified by findings
  • Report Structure: All required sections present
  • Issue Format: Grime IDs, evidence, category, severity
  • Anti-Pattern Avoidance: No Grimey Theater, Optimism Creep
  • Voice and Tone: Clinical, direct, unforgiving

Targets

  • Shell: A deliberately bad deployment script
  • Go: A deliberately bad HTTP service
  • Web: A deliberately bad Node.js endpoint

Running it

./benchmark/runner.sh --all
./benchmark/runner.sh --all --compare
